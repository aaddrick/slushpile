## 边界

插件是公开代码。工作区是某一个人的工作履历、薪酬数字和约束条件。它们是不同的东西，
住在不同的目录里，而本页几乎每一条规则都是从这一句话推出来的。

`/slushpile:onboard` 是在用户自己的目录里运行的，不是在插件的检出目录里。它把
`profile.md`、`preferences.yaml` 和 `stories.md` 写在那儿。初始化引导会明确说：
这个目录应该是一个**私有**仓库，或者干脆不是仓库；而且它不会去初始化仓库或添加远端，
因为那是一个要刻意做出的决定，不该是搭一个工作区的副作用。

## `skills/` 或 `agents/` 里不得硬编码任何关于任何用户的事实

不要薪酬下限。不要都市房租表。不要国籍，不要涉密许可状态，不要把某个具名雇主写成用户自己的，
不要具名的故事，也不要「该候选人可接受搬迁」。需要其中某一项的技能，在运行时从
`preferences.yaml` 读它。

这条规则防住的失效很具体，而且很安静。一个硬编码的薪酬下限不会报错，它会杀掉一些岗位，
看上去还杀得挺对，理由却是用户从未选择也看不见的。一个硬编码的「可接受搬迁」同样不会报错，
它会产出十二份申请，断言某个关于某人的、可能并不为真的事情。

举例时指名真实公司是可以的，而且有用，因为它们教会人这个模式。把*「大多数容量规划的候选人
都来自同一边」*作为一个依赖具体公司的论点的例子，是在教学。*「该候选人在工业控制系统领域有
十年经验」*则是一次泄漏。

请注意，第二个例子为了能出现在这一页上，不得不做了改写。真实的那个点名了一个
`check_no_pii.py` 会匹配到的领域，而这个文件正是它扫描的文件之一。这就是这道关卡按预期工作，
工作在记录它自己的那一页上。

## 这道关卡

```bash
python3 scripts/check_no_pii.py
```

它扫描 `skills/`、`agents/`、`templates/` 和 `docs/`，找的是上一次泄漏时用过的那些模式，
每一条都附着它算作泄漏的理由：作者身份、被写成用户自己的前雇主、硬编码的居住地、
硬编码的薪酬基线、被当作事实陈述的国籍或涉密许可状态、被当作事实陈述的资质证书、
真实联系方式，以及对那些只存在于本插件被产品化之前那个私有仓库里的文件的引用。

这些模式是刻意收窄的。一个会在正当散文上误报的宽泛模式，一周之内就会被压制掉，
而一项被压制的检查比没有检查更糟，因为它读起来像是已经覆盖了。

一个漏过去的新泄漏模式，该进那个脚本，而不是进一条评审意见。

## 唯一的豁免，以及它的界限

文风智能体豁免于**身份**类模式，而且仅限那些。一个文风智能体按其构造*就是*某一个人的身份：
它由那个人的写作语料生成，以其命名，其少样本示例就是那个人真实写下的句子。把身份剥掉会毁掉
这件产物本身。

联系方式在任何地方都是禁止的，文风智能体也不例外。一个随包发布的智能体里出现电话号码，
在任何说法下都是泄漏。

豁免清单是按文件、按模式列的，在 `check_no_pii.VOICE_AGENTS` 里。还有第二份清单
`ALLOWED`，给其他任何情况用，而它是刻意保持为空的。其中每一条都会是一个洞，
而这道关卡上的洞是不可见的，直到别人的申请里说自己愿意搬去一座他们从没见过的城市。

## 这条流水线从不投递任何东西

没有任何技能会碰申请门户、邮件或表单。每个阶段都只写文件。由用户来读它们，并把它们寄出去。

这首先是一条隐私性质，其次才是安全性质：一条会投递的流水线，必然是一条必须持有凭据的流水线，
而在这个设计里，没有任何地方能放它们，除非是用户自己那台机器在做某件他们没看着的事。
