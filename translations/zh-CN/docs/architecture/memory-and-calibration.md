一次求职是三个月里的四十份申请。一个没有记忆的工具，对其中每一份都按全价收费：你粘进一份
简历，拿回一个数字，关掉标签页，而这个工具结束会话时知道的东西，和它开始时知道的一模一样。

Slushpile 的记忆是一个由用户拥有的文件目录。没有数据库，没有账号，插件内部也没有任何状态：
插件是公开代码，而工作区是用户的工作履历，所以它们是两样不同的东西，被分开放在不同的地方。
参见 [personal-data.md](personal-data.md)。

## 什么是持久的

| 文件 | 由谁写入 | 由谁读取 |
| --- | --- | --- |
| `profile.md` | `onboard`，并由 `explore-experience` 和 `application-builder` 扩充 | 每一个要写散文的阶段 |
| `preferences.yaml` | `onboard`，并由 `status` 校正 | 评分、淘汰条件、审阅的调度 |
| `stories.md` | `onboard` | 构建器，在它挑出那个唯一要讲的故事时 |
| `job_search.md` | `job-board-search`、`application-builder`、`status` | 申请者池分析师、唱反调者、队列 |
| `companies.md` | `job-board-search` | 之后在同一家公司做的搜索 |
| `applications/<company>/<role>/` | `job-board-search`，之后是构建器 | 审阅，以及 `status` |

`profile.md` 不是一份简历。它是简历从中裁剪出来的那个素材池，比任何人会寄出去的东西都长上
好几倍，而它的价值在于：没有任何东西会把同样的问题再问用户一遍。

## 回写路径

有三条，每一条的存在都是因为某个阶段里学到的东西，如果留在那个阶段就毫无用处。

**审阅发现 → 画像。** 当一场审阅说某个段落单薄时，随后的访谈通常会发现这段经历是真实存在的，
只是用户从没把它写下来过。`explore-experience` 把它挖出来，它就永久进入 `profile.md`，
之后每一份申请都能取用。正是这条路径让第二十份申请的起点比第一份更好。

**结果 → 追踪文件。** 用户记录下发生了什么：无回音、电话筛选、面试、offer、拒信，以及卡在
哪个阶段。流水线里没有别的东西能产出这个，因为流水线从不投递任何东西，也从不看到回复。

**追踪文件 → 先验。** `status` 把流水线自己的预测对这些结果做回归，并把校正写进
`preferences.yaml`。

## 为什么校正写进用户数据

要记录「这条流水线对投向前沿实验室的冷投乐观了 12 个百分点」，显而易见的地方是做出这个估计的
那个智能体。那是错的地方，而且错得很安静：智能体定义是随插件一起发布的，所以在那里做的编辑
会被下一次更新无声地还原，留下一条*曾经*调好过、现在不再调好的流水线。

所以校正去了 `preferences.yaml`，它归用户所有，任何更新都不碰它。`job-board-search`
在评分时读 `calibration_priors`，而 `adversarial-review` 在调度时把这个块传给申请者池分析师
和唱反调者。

## 让校准保持诚实的那些规则

**五份已定局的申请是下限。** 低于这个数，`status` 会打印各项计数并说样本太小、不做回归，
而不是产出一张表。由两个结果算出来的比率是穿着校准外衣的噪声，而一旦它进了表，
就没人记得分母是多少了。

**沉默算作拒绝。** 投出超过 30 天且无任何回复的申请，被记为 `no_response`，而不是留在待定。
把这些排除在外，是这类表格能拿到的最大一笔乐观来源。以这种方式推断出来的数量会被报告出来。

**按实际用过的渠道来评判。** 判定按这份申请实际走的那个渠道所对应的判定分组，
绝不按最好情况的那个。拿一份冷投去对照它的温内推判定评判，正是一条流水线说服自己没错的方式。

**两个方向的误差都要报告。** 一个在 72 小时内就被自动拒掉的 INTERVIEW 判定，意味着审阅漏掉了
某个过滤器几秒钟就抓到的东西。一个转化成功了的 REJECT 意味着审阅太苛刻，而从那以后它劝退用户的
每一个岗位，都是一笔在别处根本不会出现的成本。这两者中只有一个报起来舒服，这也正是这条规则
把两个都点名的原因。

**发现要指名一个细分、一个方向和一个幅度。** 「这条流水线校准不准」无法据以行动，
任何智能体都消费不了它。「投向前沿实验室的冷投上的 INTERVIEW 判定，7 个里转化了 0 个，
而估计值是 12%」则可以被写进一条先验并据以行动。

**空先验是一个有效答案。** 只有在该渠道上有五份或更多已定局申请支撑的比率才会被写入。
其余一律保持为空，各智能体使用随插件发布的默认值，并把估计标注为未校准。一条由两个结果算出的
先验，会把评分推得比没有先验时更远离现实，而且它还带着一个经验数字的权威登场。

**在写入 `preferences.yaml` 之前会先展示 diff。** 那是用户的约束文件，而这次改动会改变今后
每一次评估的打分方式。一次没人被告知的评分改动，和流水线自己在漂移无法区分。
